# 개선 보고서 v0.8.0 — 표·도표·흐름도 중심 SI 문서 처리 방법론

- 대상: 대형 SI 프로젝트 문서 기반 FAQ 챗봇
- 상태: 1단계 표 구조 보존 코드 적용 및 인덱스 재생성 완료 / 흐름도·OCR 후속 작업
- 관련 단계: 문서 추출, 구조화, Chunking, 검색 품질 개선

## 1. 작성 목적

현재 챗봇은 PDF, DOCX, TXT, Markdown, HTML 문서에서 텍스트를 추출한 뒤 BGE-M3 임베딩과 FAISS 검색을 수행한다. 이 방식은 일반 본문 검색에는 적합하지만, 대형 SI 프로젝트 문서처럼 표·도표·흐름도·화면 캡처가 많은 문서에서는 정보 구조가 손실될 수 있다.

본 보고서는 다음 문제를 해결하기 위한 문서 처리 방법론을 정리한다.

- 표의 행과 열 관계 보존
- 흐름도의 단계와 연결 방향 보존
- 도표와 이미지 내부 텍스트 추출
- 스캔 PDF OCR 처리
- 문서의 제목·섹션·페이지 메타데이터 보존
- 구조화된 검색 Chunk 생성
- SI 프로젝트 용어와 요구사항 ID 검색 개선

## 2. 현재 방식의 한계

현재 PDF 처리 흐름은 다음과 같다.

```text file: docs/REPORT_v0.8.0_layout-aware-document-processing.md
PDF 페이지
  → pypdf.extract_text()
  → 줄바꿈과 공백 정리
  → 800자 단위 Chunk
  → BGE-M3 임베딩
  → FAISS 검색
```

### 2.1 표 구조 손실

PDF의 표가 텍스트로 추출되더라도 열 정보가 사라질 수 있다.

원본:

| 기능 | 입력 | 처리 | 출력 |
|---|---|---|---|
| 고객 등록 | 고객정보 | 유효성 검증 | 고객번호 |

단순 추출 결과:

```text file: docs/REPORT_v0.8.0_layout-aware-document-processing.md
기능 입력 처리 출력 고객 등록 고객정보 유효성 검증 고객번호
```

이 경우 모델이 값과 열의 관계를 잘못 해석할 수 있다.

### 2.2 흐름도 관계 손실

흐름도에서는 노드 위치, 화살표 방향, 조건 분기 정보가 중요하다. 단순 텍스트 추출은 다음 정보를 잃을 수 있다.

- 시작 노드와 종료 노드
- 단계 순서
- 조건 분기
- 예외 흐름
- 반복 관계
- 연결 방향

### 2.3 이미지 및 스캔 문서 누락

현재 텍스트 추출 방식은 이미지로 삽입된 다음 정보를 직접 이해하지 못한다.

- 스캔 PDF
- 도형 내부 텍스트
- 시스템 구성도
- 화면 캡처
- 그래프의 축과 범례
- 색상이나 위치로 표시된 관계

또한 현재 사용하는 `Phi-3.5-mini-instruct`는 텍스트 모델이므로 PDF 이미지 자체를 입력받아 해석하지 못한다.

### 2.4 Chunking 과정에서 구조 제거

현재 Chunking에서 줄바꿈과 공백을 정리하기 때문에 표, 제목, 절차 단계의 구조가 추가로 손실될 수 있다. 따라서 SI 문서에는 단순 문자 길이 기반 Chunking만 사용하는 것이 충분하지 않다.

## 3. 문서 유형 분류

문서마다 동일한 추출 방식을 적용하지 않고 먼저 유형을 분류한다.

| 문서 유형 | 특징 | 권장 처리 |
|---|---|---|
| 본문 중심 PDF | 선택 가능한 텍스트가 많음 | PyMuPDF 또는 pypdf |
| 표 중심 PDF | 행·열 정보가 중요함 | pdfplumber, Camelot, Tabula |
| 스캔 PDF | 이미지로만 구성됨 | OCR |
| 흐름도 중심 PDF | 노드·화살표·분기 구조 | 이미지 추출, OCR, 구조 설명 |
| 복합 문서 | 본문·표·이미지가 혼합됨 | Docling 또는 Unstructured |
| DOCX | 제목·표·문단 구조 존재 | python-docx 구조 추출 |

문서 유형은 자동 분류와 수동 확인을 함께 사용하는 것이 좋다. 페이지별 텍스트 길이가 매우 짧고 이미지 비율이 높으면 OCR 대상일 가능성이 높다.

## 4. 권장 처리 파이프라인

전체 처리 흐름은 다음과 같다.

```text file: docs/REPORT_v0.8.0_layout-aware-document-processing.md
원본 문서
  ↓
문서·페이지 유형 분류
  ↓
본문·표·이미지·도형 분리 추출
  ↓
본문: 텍스트 정리
표: Markdown 또는 key-value 변환
이미지: OCR 및 구조 설명
흐름도: 단계와 연결관계 텍스트화
  ↓
문서명·페이지·섹션·콘텐츠 유형 메타데이터 추가
  ↓
구조 기반 Chunking
  ↓
BGE-M3 벡터 인덱스 + 키워드 인덱스
  ↓
Hybrid 검색 및 재순위화
  ↓
Phi 기반 답변 생성
```

## 5. 표 처리 방법

### 5.1 표 추출

표 중심 PDF는 일반 텍스트 추출과 별도로 처리한다.

권장 도구:

- `pdfplumber`: PDF 좌표 기반 표 추출
- `Camelot`: 선이 있는 표와 격자형 표 추출
- `Tabula`: 표 영역 지정 기반 추출
- `Docling`: 레이아웃을 포함한 문서 구조 추출

표 추출 결과는 가능한 한 Markdown 또는 명시적인 key-value 텍스트로 저장한다.

### 5.2 표 구조화 예시

```text file: docs/REPORT_v0.8.0_layout-aware-document-processing.md
[표]
문서: HSL-CB-IM-010 요구사항정의서
페이지: 23
섹션: 4.2 업무 요구사항

행 1:
- 기능: 고객 등록
- 입력: 고객정보
- 처리: 유효성 검증
- 출력: 고객번호
```

또는 다음과 같이 Markdown으로 저장한다.

```markdown file: extracted_table.md
| 기능 | 입력 | 처리 | 출력 |
|---|---|---|---|
| 고객 등록 | 고객정보 | 유효성 검증 | 고객번호 |
```

### 5.3 표 Chunk 규칙

- 표 제목과 표 본문을 분리하지 않는다.
- 열 이름을 각 행에 반복하거나 명시한다.
- 한 행이 여러 Chunk로 나뉘지 않도록 한다.
- 표가 매우 크면 행 그룹 단위로 나누되 문서명·페이지·표 제목을 반복한다.
- 숫자, 코드, ID는 원문 그대로 보존한다.

## 6. 흐름도 및 도표 처리 방법

### 6.1 흐름도 텍스트화

흐름도를 이미지 그대로 임베딩하는 것보다 우선 단계와 연결관계를 명시적인 텍스트로 변환한다.

```text file: docs/REPORT_v0.8.0_layout-aware-document-processing.md
문서: HSL-CB-IM-030 작업흐름도_v3.1
페이지: 12
흐름명: 주문 처리 흐름

단계:
1. 주문 접수
2. 주문 유효성 검증
3. 재고 확인
4. 결제 승인
5. 출고 요청

연결 관계:
- 주문 접수 → 주문 유효성 검증
- 주문 유효성 검증 → 재고 확인
- 재고 확인 → 결제 승인
- 결제 승인 → 출고 요청
```

이 구조가 있으면 다음 질문에 답하기 쉬워진다.

- 주문 접수 다음 단계는 무엇인가?
- 결제 승인 전에 수행하는 작업은 무엇인가?
- 전체 주문 처리 절차를 순서대로 설명해 달라.

### 6.2 조건 분기 보존

조건 분기는 반드시 명시적으로 기록한다.

```text file: docs/REPORT_v0.8.0_layout-aware-document-processing.md
분기:
- 재고 있음 → 결제 승인
- 재고 없음 → 재고 부족 안내 후 종료
```

`예`, `아니오`, `성공`, `실패` 등의 분기 레이블과 연결 대상은 하나의 Chunk 안에 보존한다.

### 6.3 도표 처리

도표는 다음 정보를 별도로 추출한다.

- 도표 제목
- 축 이름
- 범례
- 주요 수치
- 비교 대상
- 추세 또는 관계
- 페이지 번호

그래프의 시각적 의미를 자동으로 정확하게 해석하기 어려운 경우에는 사람이 검수한 설명 텍스트를 추가하는 것이 안전하다.

## 7. OCR 처리

스캔 PDF나 이미지 중심 페이지는 OCR을 적용한다.

권장 도구:

- Tesseract OCR
- PaddleOCR
- EasyOCR
- OCRmyPDF
- Docling
- Unstructured

한국어 SI 문서는 OCR 품질을 고려해 PaddleOCR 또는 OCRmyPDF와 Tesseract 조합을 검토한다.

OCR 결과에는 다음 메타데이터를 보존한다.

- 원본 문서명
- 페이지 번호
- 이미지 영역 좌표
- OCR 여부
- 추출 텍스트
- OCR 신뢰도

신뢰도가 낮은 OCR 텍스트는 검색에는 사용하되 답변 근거로 단정하지 않도록 표시하는 것이 좋다.

## 8. 구조 기반 Chunking

### 8.1 Chunk 단위

SI 문서는 다음 구조를 보존하는 단위로 나눈다.

```text file: docs/REPORT_v0.8.0_layout-aware-document-processing.md
문서
 ├── 장
 │   ├── 절
 │   │   ├── 본문 Chunk
 │   │   ├── 표 Chunk
 │   │   ├── 요구사항 Chunk
 │   │   └── 흐름도 설명 Chunk
```

### 8.2 Chunk 메타데이터

각 Chunk에는 다음 필드를 포함한다.

```text file: docs/REPORT_v0.8.0_layout-aware-document-processing.md
문서명: HSL-CB-IM-010 요구사항정의서
문서유형: 요구사항 정의서
페이지: 23
섹션: 4.2 업무 요구사항
콘텐츠 유형: 표
프로젝트: HSL-CB
버전: V3.1
내용: ...
```

### 8.3 권장 초기값

- 일반 본문: 600~1,000자
- overlap: 80~150자
- FAQ·절차: 질문 또는 절차 단위
- 표: 행 그룹 또는 표 전체 단위
- 흐름도: 하나의 업무 흐름 또는 분기 단위
- 페이지 번호: PDF 원본 페이지 기준으로 보존

Chunk 크기는 문서 유형에 따라 다르게 적용한다. 표와 흐름도를 일반 본문과 동일한 문자 길이로 자르지 않는다.

## 9. 검색 방식 개선

### 9.1 Hybrid 검색

SI 문서에는 요구사항 ID, 인터페이스 ID, 시스템명, 화면명이 많으므로 벡터 검색만으로 충분하지 않을 수 있다.

권장 구조:

```text file: docs/REPORT_v0.8.0_layout-aware-document-processing.md
BGE-M3 의미 검색
        +
BM25 또는 TF-IDF 키워드 검색
        ↓
점수 정규화 및 통합
        ↓
후보 8~12개
        ↓
중복 제거 및 재순위화
        ↓
최종 Context 3~5개
```

키워드 검색은 다음 항목에 특히 유리하다.

- `REQ-ERP-001`
- `IF-CRM-003`
- `HSL-CB-IM-070`
- API명
- 화면 ID
- 시스템명
- 테이블명

### 9.2 재순위화

후보 Chunk를 먼저 넓게 검색한 뒤 Reranker를 적용하면 관련성이 높은 순서로 정렬할 수 있다. 다만 10GB VRAM 환경에서는 Reranker 모델이 Phi 모델과 메모리를 경쟁할 수 있으므로 CPU 실행 또는 단계적 도입을 권장한다.

## 10. LLM 및 Vision 모델 사용 여부

### 10.1 외부 LLM API 없이 가능한 작업

다음 작업은 로컬 도구만으로 가능하다.

- 본문 추출
- 표 추출
- OCR
- 표의 Markdown 변환
- 흐름도 설명을 사람이 직접 작성
- BGE-M3 임베딩
- FAISS 검색
- Phi 답변 생성

현재 환경에서는 보안상 이 방식을 우선 권장한다.

### 10.2 Vision-Language Model이 필요한 경우

다음 기능을 자동화하려면 이미지 이해 모델이 필요할 수 있다.

- 흐름도 이미지 자동 해석
- 복잡한 도표의 관계 자동 분석
- 화면 캡처에서 필드와 버튼 추출
- 그래프의 축과 추세 해석

현재 `Phi-3.5-mini-instruct`는 텍스트 모델이므로 이미지를 직접 해석하지 않는다. Vision-Language Model 또는 외부 Vision API가 필요할 수 있다.

다만 SI 문서가 외부 서버로 전송될 수 있으므로, 외부 API는 보안·계약·개인정보 정책을 검토한 뒤 도입한다. 우선은 OCR과 구조화 텍스트를 사용하는 것이 안전하다.

## 12. 검증 기준

다음 기준으로 개선 전후를 비교한다.

- 표의 행과 열 관계가 정확한가
- 흐름도 순서와 연결 방향이 정확한가
- 조건 분기를 구분하는가
- 문서명과 페이지가 정확한가
- 요구사항 ID와 인터페이스 ID를 검색하는가
- 스캔 페이지가 검색되는가
- 답변에 문서에 없는 내용을 추가하지 않는가
- 검색 시간과 답변 생성 시간이 허용 범위인가

## 13. 결론

현재 인덱싱은 일반 본문 검색에는 사용할 수 있지만 표·도표·흐름도가 핵심인 SI 문서에는 충분하지 않다. 기존 인덱스를 즉시 폐기하기보다 다음 순서로 개선하는 것이 안전하다.

```text file: docs/REPORT_v0.8.0_layout-aware-document-processing.md
현재 인덱스 보존
→ PDF 유형 확인
→ 표를 구조화 텍스트로 변환
→ 흐름도를 단계·연결관계로 변환
→ 스캔 문서 OCR
→ 문서 구조·페이지·콘텐츠 유형을 포함한 Chunk 생성
→ 인덱스 재생성
→ 표·흐름도 중심 질문으로 평가
→ 필요 시 BM25와 Reranker 추가
```

가장 먼저 적용할 작업은 **표 추출과 흐름도 설명 텍스트화**다. 이 두 작업은 외부 LLM API 없이도 수행할 수 있으며, 현재 10GB VRAM 환경과 SI 문서 보안 요구사항에 가장 적합하다.
