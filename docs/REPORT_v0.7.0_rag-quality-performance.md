# 개선 보고서 v0.7.0 — RAG 답변 품질 및 응답 속도 개선안

- 단계: 품질·성능 진단 및 개선 계획
- 상태: 1차 개선 코드 적용 완료 / 실제 SI 문서 평가 필요
- 대상: 대형 SI 프로젝트 문서 기반 FAQ 챗봇

## 1. 작성 목적

현재 챗봇은 문서 업로드, Chunk 분할, BGE-M3 임베딩, FAISS 검색, Phi-3.5-mini-instruct 답변 생성까지 연결되어 있다. 그러나 실제 사용 결과 다음 문제가 확인되었다.

- 질문 의도와 직접 관련이 없는 문서 Chunk가 검색될 수 있다.
- Chunk가 단순 문자 수 기준으로 분할되어 표, 절차, 제목과 본문 관계가 끊길 수 있다.
- 검색된 모든 Chunk가 짧은 Context에 함께 들어가 답변 근거가 흐려질 수 있다.
- 임베딩 모델을 요청마다 CPU에서 로딩할 수 있어 첫 질문과 재실행이 느리다.
- Phi 모델의 최초 로딩과 생성 시간이 길다.
- 검색 품질과 답변 품질을 측정할 평가 데이터가 없다.

본 보고서는 10GB VRAM 환경을 기준으로 품질을 우선 확보하면서 체감 응답 시간을 줄이는 단계별 방안을 제시한다.

## 2. 현재 구조와 병목

현재 흐름은 다음과 같다.

```text
질문
  → BGE-M3 질문 임베딩(CPU)
  → FAISS Top-k 검색
  → 검색 결과 3개를 Context로 결합
  → Phi-3.5-mini-instruct 생성
```

현재 주요 설정은 다음과 같다.

- 임베딩: `BAAI/bge-m3`
- 검색: 정규화 임베딩 + FAISS `IndexFlatIP`
- Chunk: 기본 800자, overlap 120자
- 검색: `top_k=3`, `min_score=0.3`
- 입력 최대 길이: 2,048 토큰
- 생성 최대 길이: 256 토큰
- 임베딩 검색: CPU 고정
- Phi 로딩: CUDA 가능 시 8비트 우선

### 2.1 품질 병목

1. **문서 구조 손실**
   - 현재 `document.text`의 공백과 줄바꿈을 합친 뒤 문자 윈도우로 나눈다.
   - 제목, 장·절, 표의 행과 열, 절차 단계가 분리될 수 있다.

2. **검색 결과의 정밀도 부족**
   - FAISS Top-k 결과만 사용하고 키워드 검색이나 재순위화가 없다.
   - SI 문서의 시스템명, 약어, 화면명, 요구사항 ID는 의미 임베딩만으로 놓칠 수 있다.

3. **Context 조립 방식 단순**
   - 검색 결과를 그대로 연결하므로 중복·무관 내용이 포함될 수 있다.
   - Context의 내용이 길어질수록 Phi가 핵심 근거를 놓칠 가능성이 커진다.

4. **답변 검증 부족**
   - 모델 출력이 실제 근거 문장을 인용하는지 자동 검증하지 않는다.
   - 질문 유형별 답변 형식이 정의되어 있지 않다.

### 2.2 속도 병목

1. 첫 질문 때 임베딩 모델과 Phi 모델을 각각 로딩한다.
2. CPU BGE-M3 임베딩은 정확하지만 질문 1건에도 상대적으로 무겁다.
3. 검색 전에 긴 질문이나 긴 Context를 그대로 처리한다.
4. Phi 모델의 최초 다운로드 및 8비트 로딩 시간이 크다.
5. Streamlit 개발 서버 재실행 시 캐시가 유지되지 않을 수 있다.

## 3. 개선 목표

실제 측정 전의 권장 목표이며, 문서 수와 GPU 상태에 따라 재조정한다.

| 항목 | 현재 추정 문제 | 1차 목표 |
|---|---|---|
| 인덱스가 있는 상태의 검색 | CPU 임베딩 지연 | 3초 이내 |
| 모델이 이미 로딩된 답변 | 긴 생성 시간 | 10~20초 이내 |
| 첫 질문 | 모델 다운로드·로딩 | 최초 1회 예외로 기록 |
| 검색 관련성 | 정량 측정 없음 | Top-3 정답 포함률 측정 |
| 답변 근거성 | 수동 확인 | 참조 Chunk 기반 수동 평가 |
| 무관 질문 | 임계값 의존 | 근거 부족 응답 안정화 |

성능 개선 전후에는 다음 시간을 분리해 기록해야 한다.

```text
임베딩 시간 + FAISS 검색 시간 + Phi 로딩 시간 + 생성 시간
```

## 4. 권장 개선 우선순위

### P0. 즉시 적용할 운영 개선

#### 4.1 모델과 임베딩 인스턴스 캐시 유지

- Streamlit에서는 `RAGService`를 `st.cache_resource`로 유지한다.
- API에서는 현재처럼 singleton 또는 `lru_cache`를 사용한다.
- Streamlit 재실행이 반복되지 않도록 파일 업로드 후에만 캐시를 clear한다.
- 사용자가 질문할 때마다 `EmbeddingIndex`를 새로 만들지 않도록 한다.

현재 UI의 `get_rag_service()` 캐시는 방향이 맞지만, 인덱스 생성 후에만 clear되는지와 프로세스가 재시작되지 않는지 확인해야 한다.

#### 4.2 답변 모델 사전 로딩 선택지 제공

첫 질문에서 긴 대기 시간이 발생하지 않도록 앱 시작 시 모델을 미리 로딩하는 선택지를 제공한다.

- 장점: 첫 답변 지연 감소
- 단점: 앱 시작 시간이 길어지고 GPU 메모리를 즉시 사용
- 권장: 운영 모드에서만 사전 로딩, 개발 모드에서는 지연 로딩

#### 4.3 질문·검색·생성 시간 로깅

각 단계의 시간을 측정하면 실제 병목을 추측하지 않고 개선할 수 있다.

```python file: app/rag.py
# 예시: 검색과 생성 시간을 별도 측정
```

로그 항목:

- query embedding milliseconds
- FAISS search milliseconds
- model load seconds
- generation seconds
- retrieved chunk count
- answer token count

### P1. 검색 품질 개선

#### 4.4 Hybrid 검색 도입

SI 문서에는 고유명사, 시스템 코드, 요구사항 ID, 화면 ID가 많으므로 벡터 검색만 사용하지 않는다.

권장 구조:

```text
BGE-M3 벡터 검색
        +
BM25 또는 TF-IDF 키워드 검색
        ↓
점수 정규화 및 결합
        ↓
후보 10개
        ↓
재순위화
        ↓
최종 Context 3~5개
```

장점:

- `REQ-ERP-001`, `IF-CRM-003`, 화면명 같은 정확한 토큰 검색 개선
- 의미가 비슷하지만 다른 업무 문서가 섞이는 현상 감소
- 시스템명과 약어 검색 개선

#### 4.5 후보 수와 최종 Context 수 분리

현재 `top_k=3`만 바로 Context로 사용한다. 다음처럼 분리한다.

- 1차 후보 검색: 8~12개
- 중복 제거: 같은 문서·같은 페이지의 중복 Chunk 제거
- 최종 Context: 3~5개
- Context 최대 문자 수 또는 토큰 수 제한

후보를 많이 가져온 뒤 최종 근거를 선별하는 편이 Top-3 고정 검색보다 안정적이다.

#### 4.6 최소 유사도 기준을 데이터에 맞게 조정

현재 `min_score=0.3`은 임의의 초기값이다. 문서와 질문을 20~50개 준비해 다음을 비교한다.

- 정답 문서가 포함되는 점수
- 무관 문서의 최고 점수
- 질문 유형별 점수 분포

그 결과를 기준으로 `0.3`, `0.35`, `0.4` 등을 비교하고, 너무 낮은 점수 결과는 Context에 넣지 않는다. 단일 임계값만으로 정확도를 보장하지 말고 Top-k와 함께 사용한다.

#### 4.7 SI 문서용 메타데이터 필터

문서 업로드 시 다음 메타데이터를 관리하면 검색 품질이 크게 개선된다.

- 프로젝트명
- 문서 유형: 요구사항·설계·운영·테스트
- 시스템명
- 버전
- 작성일
- 보안 등급
- 유효 상태

질문에 프로젝트나 시스템명이 포함되면 해당 메타데이터를 우선 필터링한다.

### P2. Chunk 품질 개선

#### 4.8 구조 인식 Chunking

현재 800자 문자 단위 분할을 다음 방식으로 개선한다.

1. Markdown 제목과 번호 체계 보존
2. PDF 페이지 경계를 유지
3. `1.`, `1.1`, `가.`, `①` 같은 절차·목차 경계 인식
4. 표는 가능한 한 하나의 단위로 유지
5. 각 Chunk 앞에 문서명·섹션·페이지를 포함
6. 너무 짧은 인접 Chunk는 결합

권장 초기값:

- 일반 본문: 600~1,000자
- overlap: 80~150자
- FAQ/절차: 질문 또는 절차 단위
- 표: 행 그룹 또는 표 전체 단위

Chunk 크기는 일괄적으로 키우기보다 문서 유형별로 다르게 적용한다.

#### 4.9 Chunk에 문서 구조를 포함

모델 Context를 다음처럼 구성한다.

```text
문서: ERP_운영매뉴얼_v2.pdf
섹션: 4. 장애 대응 > 4.2 접수 절차
페이지: 37
내용: ...
```

이렇게 하면 모델이 서로 다른 문서의 비슷한 문장을 혼동할 가능성이 낮아지고 답변 출처도 명확해진다.

### P3. 답변 생성 품질 개선

#### 4.10 질문 유형별 답변 형식

시스템 프롬프트에 다음 원칙을 명확히 넣는다.

- 절차 질문: 번호 목록
- 비교 질문: 표 또는 항목별 비교
- 정의 질문: 한 문장 정의 후 세부 설명
- 장애 질문: 증상·원인·조치·에스컬레이션
- 위치 질문: 문서명과 페이지 우선
- 근거 부족: 모른다고 답하고 부족한 정보 명시

#### 4.11 근거 인용 강제

답변에 `[근거 1]`, `[근거 2]` 형식의 인용을 포함하도록 한다. 생성 후 존재하지 않는 근거 번호가 사용되었는지 검증한다.

권장 답변 형식:

```text
답변:
...

근거:
- [근거 1] 문서명, 페이지
- [근거 2] 문서명, 페이지
```

UI의 참조 문서 표시와 별개로, 본문에도 근거 연결을 남기면 품질 검토가 쉬워진다.

#### 4.12 답변 후 검증 단계

10GB VRAM 환경에서는 별도의 검증 모델을 추가로 올리기보다 경량 규칙 검증을 우선한다.

- 답변에 문서에 없는 수치·날짜·시스템명이 추가되었는지 확인
- 답변의 근거 번호가 실제 검색 결과 범위에 있는지 확인
- 근거가 없는 경우 안전 응답으로 대체
- 검색 결과가 한 개뿐이면 확정 표현 대신 문서 기준 표현 사용

## 5. 속도 개선안

### 5.1 가장 효과적인 순서

1. Phi 모델과 BGE-M3 객체 캐시 확인
2. 최초 다운로드 완료 여부 확인
3. BGE-M3를 CPU에서 유지하되 질문 임베딩만 실행
4. 후보 검색과 Context 길이 제한
5. `max_new_tokens`를 답변 유형에 맞춰 128~192로 축소
6. 질문 정규화와 중복 검색 방지
7. 필요할 때만 GPU 임베딩을 선택적으로 평가

### 5.2 생성 토큰 제한

현재 `max_new_tokens=256`은 모든 질문에 적용된다. 단순 FAQ에는 128~160 토큰으로도 충분할 수 있다.

권장 설정 예시:

```dotenv file: .env
MAX_INPUT_TOKENS=1536
MAX_NEW_TOKENS=160
TEMPERATURE=0.1
LOAD_IN_8BIT=true
DEVICE=auto
```

주의: `MAX_INPUT_TOKENS`를 무조건 줄이면 긴 근거가 잘릴 수 있으므로 검색 Context를 먼저 정리해야 한다.

### 5.3 GPU 확인

임베딩과 FAISS가 CPU에서 동작하는 것은 현재 설계상 정상이다. GPU 사용 여부는 Phi 답변 생성 중 확인해야 한다.

```bash terminal
nvidia-smi
```

```bash terminal
.venv/bin/python -c "import torch; print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'CPU')"
```

CUDA가 사용 가능하면 Phi를 8비트로 로딩하고, GPU 메모리와 생성 시간을 측정한다. BGE-M3까지 GPU로 옮기는 것은 Phi와 VRAM을 경쟁하므로 속도 측정 후 결정한다.

## 6. 평가 데이터셋 구축

품질 개선은 대표 질문 없이 검증할 수 없다. 다음 형식의 30~50개 질문셋을 만든다.

| ID | 질문 | 기대 문서 | 기대 페이지/섹션 | 답변 핵심 | 근거 필요 |
|---|---|---|---|---|---|
| Q001 | 장애 접수 절차는? | 운영매뉴얼 | 장애대응 | 접수 순서 | 예 |
| Q002 | 시스템 연계 방식은? | 인터페이스설계서 | 연계 구성 | API/배치 구분 | 예 |
| Q003 | 문서에 없는 고객사는? | 전체 문서 | 없음 | 확인 불가 | 아니오 |

측정 항목:

- 검색 정답 포함률: Top-3, Top-5
- 답변 근거성: 0~2점
- 답변 완전성: 0~2점
- 무관 질문 거절 정확도
- 평균 검색 시간
- 평균 생성 시간
- 첫 요청과 후속 요청 시간

## 8. 권장 결론

현재는 모델을 교체하기보다 검색 품질과 Context 구성을 먼저 개선하는 것이 효과적이다. 답변 품질이 낮은 상태에서 더 큰 생성 모델을 사용하면 비용과 지연만 증가하고 근거 없는 답변은 남을 수 있다.

이번 단계에서는 다음 1차 개선을 코드에 적용했다.

- 검색 후보를 최종 `top_k`의 최대 3배까지 조회
- 동일 문서·페이지·유사 텍스트의 중복 Chunk 제거
- Context 최대 크기 제한
- SI 문서 전용 답변 지침 및 `[근거 N]` 인용 지침 추가
- 결정적 디코딩 적용
- 기본 생성 토큰을 256에서 160으로 축소
- 검색 및 생성 소요 시간 로그 추가

권장 적용 순서는 다음과 같다.

```text file: docs/REPORT_v0.7.0_rag-quality-performance.md
측정 로그 추가
→ Chunk 구조 보존
→ 검색 후보 확대 및 중복 제거
→ Hybrid 검색 도입
→ 근거 인용 프롬프트
→ 실제 SI 질문셋 평가
```

## 9. LLM API 필요 여부

현재 구조에서는 외부 LLM API가 필요하지 않다.

- 임베딩: 로컬 `BAAI/bge-m3`
- 검색: 로컬 FAISS
- 답변 생성: 로컬 `microsoft/Phi-3.5-mini-instruct`
- 실행 방식: Hugging Face Transformers

모델 가중치를 최초 한 번 다운로드하고 CUDA 또는 CPU 환경이 갖춰지면 외부 API 없이 실행할 수 있다. 다만 최초 모델 다운로드에는 Hugging Face 접근이 필요하다.

외부 LLM API는 GPU 서버를 운영할 수 없거나, 동시 사용자가 많거나, 더 높은 생성 품질과 빠른 응답이 필요한 경우 선택적으로 검토할 수 있다. 그러나 SI 문서는 고객 정보와 기밀 정보가 포함될 수 있으므로 외부 API로 전송하기 전에 보안·계약·개인정보 정책을 확인해야 한다. 현재 단계에서는 로컬 모델을 유지하는 것이 권장된다.
